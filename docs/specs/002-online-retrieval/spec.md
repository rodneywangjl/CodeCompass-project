# Spec 002: Online Query Pipeline

**Project:** CodeCompass (SE201 G1-T1) | **Sprint:** 2 | **Status:** Draft for review
**Constitution version:** 1.2.0 | **Constitution articles touched:** I, II, III, IV, V, VI, VIII, IX, X, XI (see "Constitution Check")

> This spec says **what** the online query pipeline must do and how we will know it works. It does not choose class designs, file layouts, or prompt templates beyond what the constitution already fixes; those belong in the plan.

---

## 1. Purpose

Given a developer's natural-language question about a git repository, produce a grounded, cited answer by:

1. Ensuring the index is current (calling the offline pipeline's `ensure_current`).
2. Retrieving relevant code chunks via hybrid search (semantic + keyword), merging with RRF, and re-ranking with a cross-encoder.
3. Running a bounded agent loop where a generator (Qwen2.5-Coder-Instruct via llama.cpp) may request verifier tools (`git blame`, `git log`) up to 3 times to gather commit-history evidence.
4. Checking every citation in the answer against the evidence actually in context, and flagging any that cannot be verified.

The pipeline covers every online component in the architecture diagram:

`Developer question → ensure_current → query embedder → hybrid retriever (vector ANN + BM25) → RRF merge → cross-encoder re-ranker → agent/generator → verifier tool loop → citation checker → answer (F: cited | G: flagged)`

## 2. Scope

**In scope (Sprint 2)**
- Query embedding with the same pinned embedder used for indexing.
- Semantic retrieval (vector ANN, cosine) from the Chroma index.
- Lexical retrieval (BM25) from the tantivy keyword index.
- Reciprocal Rank Fusion (RRF) merge of the two result sets.
- Cross-encoder re-ranking of the merged shortlist.
- Context assembly: formatting the top-k chunks as plain text with file/line/commit metadata for the generator.
- Generator integration via llama.cpp `llama-server` (HTTP, localhost), with switchable model profiles (`dev` 14B / `prod` 32B).
- System prompt construction and chat-template handling driven by the active profile.
- Bounded verifier tool loop: `git blame` and `git log` only, at most 3 rounds, with argument validation, caching, and per-query logging.
- Tool-call parsing from the model's text output (harness-side, no server-side tool-call features).
- Deterministic citation checker: parses the `Sources` section, matches against context, produces F (cited) or G (flagged) outcomes.
- Commit metadata (subject, author, date) in `Sources` entries copied from tool results by the harness, not generated by the model.
- A programmatic API (`ask`) and a CLI entry point.
- Stale-index fallback: if `ensure_current` fails, answer from the existing index with a visible stale-index warning.
- Per-query audit log recording: profile, model, retrieval scores, tool calls (round, tool, args, cache hit/miss), and citation-check outcome.

**Out of scope (this spec)**
- The evaluation question set and quality tuning (deferred; Article VII.1 — blocks tuning, not building).
- A web UI, authentication, multi-repository support, or hosted deployment.
- Retrieval parameter tuning (the defaults from Article IV.2 are used; changing them requires an evaluation run).
- Prompt engineering beyond a minimal, functional system prompt. Prompt quality is an evaluation-driven concern.
- Indexing commit messages or PR discussions (commit history reaches the generator only through verifier tools).
- Streaming responses.
- Sub-token or fuzzy identifier search enhancements.

## 3. Terminology

- **Context:** the set of retrieved chunks and tool results placed in the generator's input for one question.
- **Evidence:** any text in the context (chunk text, tool output) that the generator may cite.
- **Round:** one iteration of the agent loop. Round 0 is the first generator call after retrieval. Each round either produces an answer or a tool-call request.
- **Cited answer (F):** all `Sources` entries verified against context.
- **Flagged answer (G):** at least one `Sources` entry could not be matched to evidence in context.
- **Model profile:** a named configuration (`dev`, `prod`) selecting the generator model, GGUF file, server settings, context window, and generation parameters.

## 4. User Stories and Acceptance Criteria

Priorities: **P1** = required for the sprint to be done, **P2** = should ship, **P3** = nice to have.

### US1 (P1): Ask a question and get a grounded answer

*As a developer new to a repository, I want to ask a question about the code and get an answer grounded in the actual codebase, so that I can trust it.*

- **AC-1.1** Given a question and an indexed repository, when the pipeline runs, then it returns an answer with inline numbered markers and a closing `Sources` section in the constitution's fixed format (Article VI.4).
- **AC-1.2** Every factual claim in the answer is traceable to text that was placed in the generator's context (Article I.1).
- **AC-1.3** Given insufficient evidence after all allowed tool rounds, the answer explicitly states what could not be determined rather than guessing (Article I.2, I.3).
- **AC-1.4** The generator receives plain text with file/line/commit metadata, never raw vectors (Article IV.4).

### US2 (P1): Hybrid retrieval with RRF and re-ranking

*As the pipeline, I need to retrieve relevant chunks using both semantic and keyword search, merge them, and re-rank so that the best evidence reaches the generator.*

- **AC-2.1** Retrieval uses both semantic (vector ANN) and lexical (BM25) search; neither alone is used in the default configuration (Article IV.1).
- **AC-2.2** The query is embedded with the same model and revision as the index; a mismatched embedder is refused (Article II.4).
- **AC-2.3** Results from the two retrievers are merged with RRF using only rank positions: `score = sum(1 / (60 + rank))`. A chunk found by both retrievers is counted once, with contributions summed (Article IV.2).
- **AC-2.4** Default candidate sizes: top **50** from vector, top **50** from BM25; RRF-merge and keep top **50** as the re-rank shortlist; cross-encoder re-orders; top **8** go to the generator (Article IV.2).
- **AC-2.5** The RRF constant (60) and all four k values (vector k, BM25 k, rerank k, final k) are named, configurable values, not magic numbers in code (Article IV.2).
- **AC-2.6** The final k is additionally capped by the active model profile's context budget (Article IV.2, VIII.4).
- **AC-2.7** The cross-encoder re-ranker operates only on the merged shortlist, never on the whole index (Article IV.3).

### US3 (P1): Bounded verifier tool loop

*As the pipeline, I need to let the generator request git history evidence, bounded and safe, so answers can cite commit rationale.*

- **AC-3.1** The generator either answers or requests a tool call. The loop runs at most `MAX_VERIFIER_ROUNDS = 3` rounds (counted from 0). At most one tool call executes per round. When the generator answers, the system proceeds to the citation checker. If the response after the third tool round is still a tool request, the generator is called once more with tools disabled and must answer; that answer goes to the citation checker (Article V.1).
- **AC-3.2** Tools are read-only and allow-listed: `git blame` and `git log` only. No other tool is available (Article V.2).
- **AC-3.3** Tool arguments are validated: path must be inside the repository, line ranges must be in bounds, no shell interpolation (Article V.2).
- **AC-3.4** The harness executes tools; the model never gets a raw shell (Article V.2).
- **AC-3.5** Tool results are cached, keyed by `(repo, commit, path, line range, command)`, and appended to the generator's context as tool messages so they count as citable evidence (Article V.3).
- **AC-3.6** Every tool call and result is logged per query: round number, tool name, arguments, cache hit/miss (Article V.4).
- **AC-3.7** When commit history gives no useful rationale, the system says so explicitly instead of inventing a "why" (Article V.5).
- **AC-3.8** Tool calls are produced and parsed by the harness from the model's text output using a documented, tested format. The harness does not rely on any server-side tool-calling feature (Article VIII.2).

### US4 (P1): Citation integrity

*As a developer, I need to trust that cited files and commits actually appeared in the evidence, so that I don't follow fabricated references.*

- **AC-4.1** Before any answer is shown, a deterministic citation checker verifies that every cited file and commit appears in the context actually supplied to the generator (Article VI.1).
- **AC-4.2** The checker is ordinary code, not an LLM call. It is not skippable by configuration in the production path (Article VI.2).
- **AC-4.3** Outcome **F (cited answer):** all citations verified; the answer is shown normally (Article VI.3).
- **AC-4.4** Outcome **G (flagged answer):** at least one citation could not be matched; the answer is shown with (a) a visible banner stating some citations could not be verified, and (b) a clear mark on each individual unverified `Sources` entry. A flagged answer is never rendered identically to a verified one (Article VI.3).
- **AC-4.5** The checker parses the `Sources` entries and matches each file path/line range against retrieved chunk metadata and each commit hash against tool results. A cited line range matches only if every cited line lies within retrieved chunks of that file; overlapping a chunk is not enough. A marker with no matching entry, or an entry matching nothing in context, makes the answer flagged (Article VI.4).
- **AC-4.6** Commit subject, author, and date in a `Sources` entry are copied by the harness from the tool result, not generated by the model (Article VI.4).
- **AC-4.7** The checker verifies existence in context, not correctness. Documentation does not imply "verified" means "true" (Article VI.5).

### US5 (P1): Generator integration via llama.cpp

*As the pipeline, I need to call the generator through llama-server with the correct profile settings.*

- **AC-5.1** The generator is selected through named model profiles in configuration (`dev` = 14B, `prod` = 32B), chosen by one setting or environment variable (`GENERATOR_PROFILE`). Switching models requires no code change (Article VIII.4).
- **AC-5.2** Each profile defines: model id, GGUF file and checksum, server launch settings, quantisation, context window, and generation parameters, including a seed for reproducibility (Articles VIII.4, VII.6).
- **AC-5.3** All generator access goes through one interface; no other module imports a model library or names a model directly (Article VIII.4).
- **AC-5.4** The generator interface talks to `llama-server` over local HTTP using a standard HTTP client. `llama-cpp-python` is not used (Article VIII.2).
- **AC-5.5** The server binds to localhost only (`127.0.0.1`) unless a deployment spec says otherwise (Article VIII.2).
- **AC-5.6** Chat-template handling, stop tokens, and request/response parsing live only inside the generator wrapper (Article VIII.2).
- **AC-5.7** Prompt templates, context budgeting, and tool-call parsing are driven by the active profile and work with both models (Article VIII.4).
- **AC-5.8** The active profile and resolved model id are logged at startup and recorded on every per-query log (Article VIII.4).
- **AC-5.9** The default profile is `dev`. An unknown profile causes a loud startup failure, not a silent fallback (Article VIII.4).
- **AC-5.10** Server start-up, health check, and shutdown are handled in one documented place (Article VIII.2).
- **AC-5.11** CPU-only operation remains possible; code does not assume a specific GPU API or model size (Article VIII.2).
- **AC-5.12** Before the first query, the system checks that the running server can serve the active profile (its context size is at least the profile's context window, and it has the profile's model file loaded when one is pinned), and fails loudly otherwise (Articles VIII.2, VIII.4).

### US6 (P2): Index freshness before answering

*As the pipeline, I must ensure the index is current before answering, and handle failures gracefully.*

- **AC-6.1** Before answering each question, the pipeline calls the offline pipeline's `ensure_current` (Article III.2).
- **AC-6.2** If `ensure_current` succeeds, the answer is produced from the current index.
- **AC-6.3** If `ensure_current` fails, the answer is produced from the existing (stale) index and clearly flagged as based on a stale index. The system does not hang or silently answer from stale data (Article III.2).

### US7 (P2): Audit logging

*As a team reviewing answers, I need a complete per-query log so I can reproduce and audit any answer.*

- **AC-7.1** Every query produces a structured log containing: question text, active profile, resolved model id, retrieval scores (per-chunk RRF and re-ranker scores), tool calls (round, tool, arguments, result summary, cache hit/miss), citation-check outcome (F or G with details), and timing.
- **AC-7.2** The log is written to a per-query file (or a structured log stream) that is queryable after the fact.
- **AC-7.3** The stale-index warning, if triggered, is recorded in the log.

### US8 (P2): CLI entry point

*As a developer, I want to ask a question from the command line.*

- **AC-8.1** A CLI command accepts a repository path, a question, and an optional profile name, and prints the answer with citations.
- **AC-8.2** Flagged answers display the banner and per-source marks in the terminal output.
- **AC-8.3** Stale-index warnings are displayed before the answer.
- **AC-8.4** A `--verbose` flag prints retrieval details (chunk paths, scores) and tool-call summaries.

### US9 (P3): Programmatic API

*As a future web UI or integration, I need a function I can call.*

- **AC-9.1** A single `ask(repo_path, question, *, config, profile)` function returns a structured result containing: answer text, sources list (with verification status per source), citation outcome (F or G), stale-index flag, and the audit log.
- **AC-9.2** The function does not print to stdout; all output is returned in the result object.

## 6. Edge Cases

Each of these needs at least one test:

- A question that returns no relevant chunks from either index (the answer should say "I could not find enough evidence").
- A question that matches BM25 but not the vector index (and vice versa) — both paths must contribute.
- A chunk found by both retrievers is counted once in RRF, not duplicated.
- A tool call with a path outside the repository is rejected with a clear error.
- A tool call with a line range out of bounds is rejected.
- A tool call argument containing shell metacharacters is sanitised or rejected.
- The generator requests 3 tool rounds and then the loop terminates.
- The generator requests a tool that is not in the allow list — rejected.
- The generator produces a citation to a file not in the retrieved context — flagged.
- The generator produces a citation to a commit not in any tool result — flagged.
- All citations are valid — cited (F).
- The generator produces no `Sources` section — the answer should be flagged. **[NEEDS CLARIFICATION]** This also flags an honest "I could not determine X" answer (Article I.3) with the unverified-citation banner, which wrongly suggests a fabricated citation. Options: (a) keep outcome G but show a distinct "no sources were cited" message instead of the unverified-citation banner; (b) the harness, not the model, writes the no-evidence answer when retrieval finds nothing, and every generator answer must cite. Treating an uncited answer as F is not an option: it would let uncited claims through.
- The answer references a source marker `[N]` but there is no `[N]` entry in `Sources` — flagged.
- `ensure_current` fails (e.g. lock timeout) — answer from stale index with warning.
- `ensure_current` succeeds but the index is empty (no chunks) — answer says no evidence found.
- The `llama-server` is not running or unreachable — fail with a clear error, not a hang.
- The generator produces malformed tool-call syntax — the harness treats it as a final answer (not a crash).
- A very long answer that would exceed the context window — context budgeting caps the number of chunks.
- A tool result larger than the per-result cap is truncated with a visible marker; across all allowed tool rounds the conversation never exceeds the context window.
- A citation whose line range overlaps a retrieved chunk but extends beyond it — flagged.
- The generator still requests a tool after the third tool round — one final answer-only call is made and the loop ends.
- Concurrent questions (two `ask` calls) — each gets its own context; tool cache may be shared.

## 7. Non-Functional Requirements

- **Determinism (given fixed model output):** same question, same index, same model output produces the same answer, same citations, same audit log. The citation checker and RRF merge are fully deterministic. Generator output may vary (temperature > 0) but the surrounding pipeline is deterministic given the same model response.
- **Locality:** nothing leaves the machine by default (Article X.4, VIII.7). The generator runs locally via llama-server; the embedder and re-ranker run locally.
- **Portability:** runs on Linux, Windows, and macOS. llama-server is cross-platform (Article VIII.2).
- **Isolation:** the required test suite runs with no GPU, no network, no model download, no `llama-server`. A stub generator returns deterministic canned responses. Real-model tests are `model`-marked and run locally (Article IX.7, VIII.6).
- **Latency:** no numeric target in Sprint 2. The audit log records per-stage timings (retrieval, re-ranking, generation per round, tool execution, citation check) so a target can be set from measurements.
- **Dependencies:** libraries and model revisions are pinned (Article VIII.1, VIII.3). New dependencies require approval.

## 10. Test Strategy (feeds the TDD cycle)

Every AC above becomes one or more tests written **before** the code that satisfies it (Article IX.3).

**Stub generator.** A deterministic stub that returns canned responses (with and without tool-call requests, with valid and invalid citations) so the required suite needs no `llama-server`, no GPU, and no model download.

**Stub re-ranker.** A deterministic stub that re-orders by a fixed scoring function (e.g. text-length or alphabetical) so cross-encoder tests are model-free.

**Fixture repository.** The existing scripted fixture repo from Sprint 1, extended if needed with additional commits that have meaningful commit messages for verifier-tool testing.

| Test level | What it covers |
|------------|----------------|
| Unit | RRF merge (scoring, deduplication, edge cases), context assembly (formatting, budget capping), tool-argument validation, tool-call parsing, tool-result caching, citation checker (F and G outcomes, all edge cases), source-entry parsing, model-profile loading |
| Integration (stub generator + stub re-ranker) | Full `ask` pipeline: retrieval → RRF → re-rank → generate → tool loop → citation check; stale-index fallback; empty-index handling; round-limit enforcement; flagged vs cited answers |
| `model`-marked (local only) | Real generator produces an answer with valid citations on the fixture repo; real cross-encoder re-ranks correctly; end-to-end smoke with both `dev` and `prod` profiles |

**Required regression tests** (from Article IX.5): a citation to a non-retrieved file is flagged; the round limit terminates the loop.

**Definition of done for this spec:** all ACs for P1 and P2 stories have approved, passing tests; the full required suite is green in CI; the citation checker correctly classifies F and G outcomes on fixture data; no skipped or xfail tests without a linked justification.

## 11. Clarifications

| # | Question | Decision |
|---|----------|----------|
| C1 | System prompt content | A minimal, functional system prompt is hardcoded in the plan (not the spec). Prompt engineering is deferred until the evaluation set exists (Article VII.1). The prompt instructs the model to cite using the fixed format and to request tools when commit rationale is needed. |
| C2 | Tool-call format | The harness defines a simple text format (e.g. `<tool>tool_name(arg1, arg2)</tool>`) documented in the plan. The model is prompted to use it. The format is parsed deterministically; malformed tool calls are treated as final answers. |
| C3 | Context budget | Measured in tokens using the embedder's tokenizer. The budget is `context_window - system_prompt_tokens - generation_reserve`, and the number of chunks is reduced until the assembled context fits. This is a profile-driven value. |
| C4 | Re-ranker model | `BAAI/bge-reranker-v2-m3` (Article VIII.1). Runs locally via `sentence-transformers` or the `FlagEmbedding` library. Pinned version. |
| C5 | Cache scope | Tool-result cache is keyed by `(repo_path, commit_sha, tool, args)` and lives for the duration of one `ask` call. Persistent cross-query caching is deferred. |
| C6 | Concurrent queries | Each `ask` call gets its own context and audit log. The tool cache is per-call. Index access uses the read-only handles from `open_index`. No shared mutable state between queries. |
| C7 | `git log` scope | `git log` is scoped to a specific file path and limited to a configurable number of commits (default: 20). The harness enforces this limit. |
| C8 | `git blame` scope | `git blame` is scoped to a specific file path and optional line range. The harness validates the path and range. |
| C9 | Server lifecycle | For Sprint 2, `llama-server` is assumed to be started externally (manually or by a script). The `ask` function connects to a configured URL. A health-check is performed before the first query. Server lifecycle management is documented but not automated in Sprint 2. |
| C10 | Tool calls per round | One. Only the first tool call in a response is executed; Article V.1's limit of 3 rounds therefore means at most 3 tool executions per question. |
| C11 | Commit the tools run against | The indexed commit, not HEAD, so `git blame` line numbers match the retrieved chunks even when the index is stale. |
| C12 | "Tool messages" (Article V.3, AC-3.5) | Read as "messages that carry tool results", not the chat API's `tool` role, which belongs to the server-side tool-calling feature the harness must not use (Article VIII.2). Tool results are sent as `user`-role messages wrapped in `<tool_result>` tags (plan D16). If reviewers read V.3 as requiring the `tool` role, that needs a PATCH clarification amendment to the constitution. |
